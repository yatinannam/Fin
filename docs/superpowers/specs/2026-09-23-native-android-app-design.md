# Flat Ledger: Native Android App Design

## Goal

Turn Flat Ledger from a single-file web page into a real installable Android
app with durable local storage and a CSV export/share feature, so it's safe
to use for tracking actual money and rent-splitting data.

## Current state (for reference)

- Single `index.html` at repo root: inline `<style>` and inline `<script>`.
- Persistence: `localStorage` (key `flat-ledger-data-v1`), capped at 200
  transactions, with a fallback attempt at a Claude-artifact-only
  `window.claude.use('db')` capability. That capability only exists when the
  page is hosted as a Claude artifact — it is dead code once this becomes a
  standalone app and will be removed.
- `manifest.json` + `service-worker.js` make it installable as a PWA today,
  but that path is being superseded by the native app per user decision.

## Non-goals

- No iOS build (Android only, per decision).
- No cloud sync / multi-device sync. Local-only storage on the phone.
- No data import/restore feature in this pass — export only. (Can be added
  later using the same SQLite layer.)
- No redesign of the UI/UX. Passbook view, envelopes, bottom sheets, and the
  light/dark theme all carry over unchanged.
- Not publishing to the Play Store in this pass — sideloaded APK / run via
  Android Studio to a connected device or emulator.

## Architecture

Repo becomes a Capacitor project. Layout:

```
Fin/
  www/                      # web assets Capacitor packages into the app
    index.html              # markup only
    styles.css              # extracted from the old inline <style>
    storage.js               # new data layer — SQLite-backed
    app.js                   # UI rendering + event handlers
  android/                  # generated by `npx cap add android`
  capacitor.config.json
  package.json
  icon-192.png, icon-512.png  # kept, reused for Android launcher icon generation
  manifest.json, service-worker.js  # kept as-is; harmless if unused, low cost to leave
  docs/superpowers/specs/...
```

The current inline script is split into `storage.js` (persistence) and
`app.js` (rendering/DOM/event wiring) because the persistence layer is
changing from synchronous `localStorage` calls to async SQLite calls —
that async boundary is the natural seam to split the file on. This is not
a general refactor of the UI code; `app.js` keeps the same render()/event
handler structure that exists today, just reading from `storage.js`
instead of manipulating `localStorage` directly.

## Storage layer

**Plugin:** `@capacitor-community/sqlite`, giving a real on-device SQLite
database file instead of `localStorage` (which can be cleared by the OS
under storage pressure or when app data/cache is cleared — not acceptable
for money data).

**Schema:**

```sql
CREATE TABLE envelopes (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  allocated REAL NOT NULL DEFAULT 0,
  spent REAL NOT NULL DEFAULT 0
);

CREATE TABLE transactions (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,       -- 'income' | 'expense' | 'allocate' | 'move'
  amount REAL NOT NULL,
  title TEXT NOT NULL,
  sub TEXT,
  envelope_id TEXT,          -- nullable; set for expense/allocate rows
  ts TEXT NOT NULL           -- ISO timestamp, same format as today
);

CREATE TABLE meta (
  key TEXT PRIMARY KEY,
  value TEXT
);
-- meta holds a single row: key='unallocated', value=<current unallocated amount>
```

The 200-transaction cap is removed — SQLite has no practical reason to
cap history, and "all the logs" was an explicit requirement.

**`storage.js` API** (small, so `app.js` doesn't need to know SQL):

```js
Storage.init()                     // opens/creates the DB, runs schema if needed
Storage.getState()                 // -> { unallocated, categories, transactions }
Storage.addIncome(amount, note)
Storage.addEnvelope(name, initial)
Storage.logExpense(envelopeId, amount, note)
Storage.allocateMore(envelopeId, amount)
Storage.deleteEnvelope(envelopeId)
Storage.reset()
Storage.getAllTransactionsForExport()  // -> array of rows, unpaginated
```

Each mutating call performs its SQL writes and returns the fresh state,
mirroring the current pattern where every action recomputes and re-renders
state. Amount rounding (`round2`) stays exactly as it is today, applied
before every write.

Money amounts are stored as `REAL` for consistency with the current numeric
model (no behavior change to rounding); this matches what exists today
rather than introducing an integer-cents migration, which is out of scope.

**Startup:** `app.js` calls `Storage.init()` then `Storage.getState()`
before first render, replacing today's `init()`/`getDbRef()`/`loadLocal()`
logic. No migration path from old `localStorage` data is needed — this is
a fresh native app install, not an upgrade of the existing PWA install.

## Export feature

New button (e.g. next to "Reset" in the header) — "Export CSV".

Flow:
1. `Storage.getAllTransactionsForExport()` returns every transaction row.
2. Build a CSV string client-side: header row
   `Date,Type,Title,Note,Envelope,Amount`, one row per transaction, amounts
   as plain numbers (no currency symbol, so it opens cleanly in
   Sheets/Excel).
3. Write it to a temp file via `@capacitor/filesystem`
   (`Directory.Cache`, e.g. `flat-ledger-export-<timestamp>.csv`).
4. Invoke `@capacitor/share`'s `Share.share()` with that file URI, which
   opens Android's native share sheet (Drive, email, WhatsApp, etc. — per
   decision).

No new permissions are required beyond what these two plugins declare by
default (cache-directory writes don't need storage permission on modern
Android).

## Error handling

- `Storage.init()` failure (e.g. plugin not available) shows a full-screen
  error state instead of silently falling back to `localStorage` — for
  money data, a loud failure is safer than a silent divergent data source.
  This intentionally removes today's silent local-storage fallback
  behavior now that SQLite is the only supported store.
- Export failure (e.g. no share target available) shows an inline error
  message in the export UI rather than failing silently.
- All existing input validation (amount > 0, envelope required, don't
  allocate more than unallocated) is unchanged.

## Dev setup (one-time, documented alongside this work)

1. Install Android Studio (includes the Android SDK and an emulator
   manager).
2. `npm init -y` (if no package.json yet), then
   `npm install @capacitor/core @capacitor/android @capacitor-community/sqlite @capacitor/filesystem @capacitor/share`
   and `npm install -D @capacitor/cli`.
3. `npx cap init "Flat Ledger" com.<yourname>.flatledger --web-dir=www`
4. `npx cap add android`
5. Loop: edit files under `www/` → `npx cap sync android` → open
   `android/` in Android Studio → Run on emulator or a USB-connected phone
   (with USB debugging enabled in Developer Options).

This will be written up as a short `SETUP.md` so it doesn't need to be
re-derived later.

## Testing

- Manual pass on an emulator (or the user's phone) covering: add income,
  create envelope, allocate more, log expense, delete envelope (balance
  returns to unallocated), reset, and export CSV — opening the exported
  file in a spreadsheet app to confirm the data round-trips correctly.
- No automated test suite exists today and none is being introduced here —
  consistent with the app's current scope (a small personal tool), and
  out of scope for this pass.

## Open items intentionally deferred

- Import/restore from a CSV or JSON backup.
- Play Store packaging (signing config, versioning).
